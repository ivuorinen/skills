# CodeQL runs on every PR but is not a required check, so a PR merges with new alerts

## Problem

The CodeQL workflow runs on every pull request and produces per-language check runs.
The `main` ruleset does not require them. The analysis looks like a gate, reports like a
gate, and blocks nothing.

## Evidence

The live ruleset lists three required checks and no CodeQL leg:

```text
$ gh api repos/ivuorinen/skills/rulesets/15530545
{"checks":["Validate","Lint PR title","Lint commit messages"],"codeowner":[true],"name":"main"}
```

The workflow does run on pull requests, over a two-language matrix, so the check runs
exist under the names `Analyze (python)` and `Analyze (actions)`:

```text
.github/workflows/codeql.yml:19-23
on:
  push:
    branches:
      - main
  pull_request:
.github/workflows/codeql.yml:39,50
    name: Analyze
        language: [python, actions]
```

## Impact

A pull request introducing a Critical or High CodeQL alert merges without obstruction.
The alert appears in the Security tab after the fact, on `main`, where fixing it costs a
follow-up pull request rather than a push to the branch under review. This is the
non-gating-check class the `ci` command exists to find, and this branch spent several
commits closing CodeQL findings, so the workflow is actively relied upon.

## Fix

Add both matrix legs to the ruleset's required status checks:

```bash
gh api -X PUT repos/ivuorinen/skills/rulesets/15530545 \
  -f 'rules[][type=required_status_checks]' ...
```

naming `Analyze (python)` and `Analyze (actions)` alongside the three existing contexts.
Adding the bare `Analyze` name will not work, because the matrix expands the job name.

If non-blocking is deliberate, record that in `.claude/rules/github-actions-security.md`
with the reason, so the next reader does not have to infer it from a ruleset they cannot
see from a checkout.

Note the same query confirmed `require_code_owner_review` is true, so the control
`.claude/rules/vendored-skills.md` calls load-bearing is live.
